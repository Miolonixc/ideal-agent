# План развития ideal-agent

Актуально для ветки `beta` после коммита `6d968b9`.

## Текущее состояние

Базовый агент работоспособен: полный набор Python-тестов проходит, HTTP-интерфейс
по умолчанию локальный, поддерживает токен, а Android-компаньон собирается в
GitHub Actions. Критические проблемы исходной версии закрыты: публичный HTTP
без аутентификации, подмена LLM endpoint из запроса и выход `grep` за workspace.

До production-готовности остаются следующие риски:

- жизненный цикл SQLite-соединений, сокетов и MCP-процессов не управляется
  централизованно;
- IDE и Telegram-каналы требуют такой же чёткой модели аутентификации, как HTTP;
- sandbox зависит от внешних утилит и пока не имеет интеграционных тестов на
  Linux;
- инструменты skills и MCP считаются доверенными, но это явно не фиксируется в
  модели разрешений;
- Android-клиент прошёл CI-сборку, но не имеет UI/сетевых тестов.

## Этап 1 — надёжность и безопасность ядра

Приоритет: P0/P1. Цель — безопасная эксплуатация агента с долгоживущими
каналами.

1. Ввести единый жизненный цикл `Agent.close()`.
   - Закрывать `AuditLog`, `MemoryStore`, RepoIndex и все MCP-клиенты.
   - Вызывать закрытие при завершении CLI, HTTP, IDE и Telegram-сервисов.
   - Закрывать listening/client sockets в `SocketChannel`.
   - Критерий: тесты выполняются с `ResourceWarning` как ошибкой без утечек,
     кроме ресурсов тестовых заглушек.

2. Усилить сетевые каналы.
   - IDE: токен handshake, лимит размера строки, таймауты, обработка нескольких
     подключений или явное ограничение одного клиента.
   - Telegram: запрещать запуск без `telegram.allowed`, кроме явного
     `IDEAL_ALLOW_PUBLIC_TELEGRAM=1`.
   - HTTP: добавить ограничение длины `text`, rate limiting на токен/IP и
     документировать обязательный TLS при использовании не на localhost.
   - Критерий: негативные тесты для отсутствующего/неверного токена, oversized
     запросов и конкурентных сессий.

3. Довести sandbox до проверяемого контракта.
   - Вынести политику sandbox в конфиг (`required`, `best-effort`, `disabled`).
   - Для Linux в CI запустить интеграционные тесты bwrap/unshare: нет сети,
     запись разрешена только в workspace, чтение вне него блокируется.
   - Не выполнять shell при `required` и недоступном sandbox.
   - Критерий: отдельная job `sandbox-tests` на Ubuntu.

## Этап 2 — корректность агентного цикла

Приоритет: P1. Цель — предсказуемое выполнение длительных задач.

1. Сделать схемы и результаты tools строгими.
   - Валидировать JSON-аргументы против минимальной JSON Schema до вызова tool.
   - Хранить структурированный результат: `ok`, `output`, `error`, `truncated`.
   - Добавить лимиты размера `read_file`, `grep`, stdout/stderr и число файлов.

2. Улучшить обработку ошибок провайдеров.
   - Нормализовать сетевые ошибки и HTTP-коды всех LLM-провайдеров.
   - Добавить retry только для безопасных transient-ошибок, с exponential backoff.
   - Покрыть пустой ответ, неполный stream, malformed tool-call и timeout.

3. Разделить контекст и память по workspace/проекту.
   - Память должна иметь namespace от канонического пути workspace.
   - RepoIndex нужно кэшировать с fingerprint файлов, а не строить целиком на
     каждый новый процесс.
   - Критерий: контекст одного проекта не появляется в другом.

## Этап 3 — skills, MCP и расширяемость

Приоритет: P1/P2.

1. Ввести manifest разрешений для skills и MCP.
   - Явно отмечать: filesystem, network, shell, secrets.
   - Отдельное подтверждение для первого запуска непроверенного расширения.
   - Запретить коллизии имён со встроенными tools без явного namespace.

2. Сделать MCP-клиент устойчивым.
   - Ограничить stdout/stderr, корректно завершать дочерний процесс, проверять
     его код завершения и поддерживать request cancellation.
   - Добавить таймауты на initialize/list/call и тест аварийного MCP-сервера.

3. Добавить developer UX.
   - Команда `/audit` для последних tool-вызовов и `/health` для статуса каналов.
   - `--dry-run` для вывода предполагаемых действий без исполнения.

## Этап 4 — Android-компаньон

Приоритет: P2.

1. Закрыть логические сценарии клиента.
   - Явный экран состояния подключения: offline/connecting/connected/error.
   - Возможность отменить streaming-запрос и корректно закрыть соединение.
   - Валидация host:port, HTTPS для удалённого хоста, понятная ошибка 401.

2. Закрепить дизайн-систему.
   - Светлая/тёмная темы и динамические цвета Material You.
   - Единые токены отступов, цветов статусов и состояний кнопок.
   - Доступность: content descriptions, увеличенный шрифт, контраст,
     touch-target не меньше 48dp.

3. Автоматизировать проверку.
   - Добавить unit-тесты markdown-парсера, ограничения вложений и JSON/SSE.
   - Добавить Compose UI-тесты: отправка, ошибки сети, настройки и список сессий.
   - В CI публиковать APK и, при необходимости, скриншоты smoke-теста.

## Этап 5 — релизный контур

Приоритет: P2.

1. Версионирование и changelog.
   - Автоматически синхронизировать Android `versionCode`/`versionName` с тегом.
   - Вести `CHANGELOG.md` и release notes.

2. Supply-chain и выпуск.
   - Заменить debug keystore на подписывание release APK через GitHub Secrets.
   - Добавить SHA-256 и SBOM к артефактам.
   - Создавать GitHub Release для подписанного APK после ручного approval.

3. Метрики без утечки содержимого.
   - Опциональные локальные метрики длительности tool/LLM-вызовов.
   - Никогда не записывать промпты, API-ключи и вложения в telemetry.

## Рекомендуемый порядок ближайших PR

1. `fix: close agent resources and secure IDE/Telegram channels`
2. `test: add sandbox and HTTP negative integration coverage`
3. `feat: validate tools and namespace project memory`
4. `feat(android): connection states, cancellation and UI tests`
5. `release: signed APK pipeline and changelog`
